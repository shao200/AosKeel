# 01 · 基础概念：从"知识"到"可执行的语义骨架"

> 信息性文档，不产生规范条款。规范性定义以 [aos-spec.md §1.1 术语表](../aos-spec.md) 为准。

## 结论先行

**AI 本体论（Ontology）是对特定领域中概念、关系、属性与规则所做的显式、形式化结构化定义。** 它最近被重新发现的价值不在哲学层面，而在工程层面：大模型"有知识但不懂结构"，本体为它补上**结构化知识骨架 + 业务规则手册**，让回答与行动有据可依、有规可循。

**AosKeel 的关键增量**：传统本体（含知识图谱）主要回答"世界是什么"；AOS 的四元组把 **ActionType（状态变更契约）** 提升为与 ObjectType 并列的一等元，于是本体同时回答"世界是什么"**和**"谁能在什么条件下改变世界、改变后如何被审计"。这是从描述性本体到**治理性本体**的跃迁。

---

## 1. 为什么大模型需要本体

| 现象 | 根因 | 本体给出的机制 |
|---|---|---|
| "知识渊博但有时会胡说" | LLM 生成的是文本序列，不是受约束的断言 | 断言必须经声明的 Action 追加事件；未注册的能力不存在写路径（INV-1 / INV-13） |
| 实体关系与边界条件靠语境推断 | 自然语言规范隐含大量未言明前提 | 类型、必填、基数、引用存在性在注册期编译为 Check AST（KS-7.1） |
| 生成代码"看似合理却偏离业务" | 语义漂移（semantic drift） | 九类声明是唯一语义真相源，`declared == registered` 持续对账（KS-7.2 第 5 步） |
| 无法回答"它当时依据什么做决定" | 推理过程不留痕 | 决策事件双引用（投影标识+transaction_time / 会话事件引用）与解释器审计（KS-2.5 / KS-3.3） |
| 权限写在提示词里，靠自觉 | 概率性约束不是约束 | Agent 能力面 = 能力清单 ∩ 授权矩阵的**严格子集**，越权在触达存储前拒绝（P-10 / INV-4） |

两条驱动力解释了这波热潮：① **大模型落地的刚需**——企业严肃场景要求可推理、可审计，LLM 单独做不到；② **Palantir 的示范效应**——其 Ontology 在军工、金融、工业领域把"对象/属性/链接/行动"建成企业级 AI 基础设施，展示了巨大的工程价值。AOS 借鉴的是这种工程形态，并额外给出治理层与机械核对点。

> **判据**：凡"错误代价远大于建模成本"的领域（金融敞口、临床试验、合约审批、国防决策、关键基础设施），本体投资的收益才成立；小团队场景存在过度工程风险（规范 §9.1，信息性）。

## 2. 什么是本体论：显式化隐含知识

一个**简单定义**：本体论是对某领域中的**概念、关系、属性以及规则**所做的显式、形式化结构化定义。核心价值是把人类知识中**隐含的、语境化的**部分，转成机器可理解、可验证、可推理的明确规则。

把它想象成一张标准化的**概念地图**：

- 在电商系统里，数据库只关心怎么存"用户 ID"和"商品 ID"；
- 本体则必须定义清楚：**"用户"是什么**、**"商品"是什么**、二者之间**"购买"关系的准确含义**是什么，以及**"支付成功"是"发货"的前置规则**。

数据库管的是**存储形态**；本体管的是**语义与规则的边界**。前者回答"数据长什么样"，后者回答"什么算合法、什么能推出什么"。

### 2.1 本体的四个基本构件（通用表述）

| 构件 | 英文 | 回答的问题 | 例子 |
|---|---|---|---|
| 类 | Class | 有哪些概念范畴 | 患者、药物、订单 |
| 属性 | Property | 类有什么特征 | 患者.年龄；订单.金额 |
| 关系 | Relation | 类之间如何关联 | is-a（医生⊂员工）、part-of（订单行⊂订单） |
| 公理 / 规则 | Axiom / Rule | 什么必须成立、什么被禁止 | "每个订单必须且只能关联一个客户"；"若患者对某药过敏，禁止开具该药" |

第四项是推理能力的来源：没有公理的"概念地图"只是标签体系，有公理才开始具备**可判定性**。

## 3. 知识图谱 = 本体 + 实例：蓝图与建筑

最经典的比喻：**本体论是建筑设计的图纸，知识图谱是按图纸盖好的大楼。**

更技术化的表述：

```
知识图谱 = 本体（语义 Schema / 模式层，TBox） + 实例数据（数据层，ABox）
```

### 3.1 上层 TBox（Terminological Box，术语盒 / 模式层）

定义"蓝图"——允许存在哪些**类型**的实体、哪些**类型**的关系，规定概念框架与规则：

- **类（Class）**：领域核心概念范畴，如"患者""药物""订单"；
- **属性（Property）**：分**数据属性**（患者有"年龄"）与**对象属性**（患者**服用了**药物）；
- **关系（Relation）**：`is-a`（继承）、`part-of`（组成）等类间关联模式；
- **公理 / 规则（Axiom / Rule）**：逻辑约束，例如"每个订单必须且只能关联一个客户"、"患者过敏则禁止开药"。

### 3.2 下层 ABox（Assertion Box，断言盒 / 数据层）

按 TBox 蓝图填充的具体数据，构成"大楼的血肉"：

- **个体（Individual）**：某个类的具体实例，如患者"张三"、药物"阿司匹林"；
- **断言（Assertion）**：关于个体的事实，最基本形式是**三元组（Triple）** `(主语, 谓词, 宾语)`：`(张三, 服用, 阿司匹林)`、`(张三, 年龄, 45)`。

**关系小结**：知识图谱是本体论的**实例化与物理实现**——用"实体-关系-实体"的三元组网络，承载按本体规范组织起来的海量具体知识。本体变了，图纸变了；实例跟着改，但不能违背图纸。

## 4. Palantir 风格工程对照（教学类比）

Palantir Ontology 的工程实践把上述双层落实为可操作的构件。用它做桥接，便于从熟悉的术语切入：

| 层级 | Palantir 术语 | 对应本体论概念 | 示例 |
|---|---|---|---|
| **TBox（模式层）** | Object Type | 类（Class） | `CustomerOrder`（客户订单） |
| | Property | 属性（Property） | `status`（状态） |
| | Link Type | 关系（Relation） | `contains`（包含） |
| **ABox（数据层）** | Object | 个体（Individual） | 订单 `HC-SO-260801` |
| | Property Value | 断言的值 | 该订单的 `status = Confirmed` |
| | Link | 断言的关联 | 订单 `HC-SO-260801` **`contains`** 订单行 `...-10` |

> **类比的边界**（必须说清，否则会误判项目）：上表是**通用工程形态**，不是 AOS 的实现清单。AOS 的对应物不同——见下一节。尤其：AOS 的 LinkType 不是普通的"对象链接"，而是**零属性 + 遍历透明 + 系统写入**的"结构性链接"（T09 / P-4）；它故意**不承载业务语义、不授予任何权限**（INV-2）。

## 5. 从知识图谱到 AOS：四元组与四构造

AOS 的术语表（规范 §1.1）定义了两个核心组合，它们是理解整个项目的钥匙。

### 5.1 T01 四元组（描述"一个领域由什么构成"）

```
ObjectType / Property / LinkType / ActionType
```

| 元 | AOS 定义 | 与经典本体的差别 |
|---|---|---|
| ObjectType | 对象的类型 | 对应 Class |
| Property | 属性 | 对应 Property；额外可标 `decision_relevant`（是否决策依据，INV-8） |
| LinkType | 类型间的链接 | **零语义结构性链接**，跨上下文用 `same_as`，禁止绑定 Action（INV-2 / VER-21） |
| **ActionType** | **声明式状态变更契约**：参数、SC、权限、副作用、审计要求的注册单元 | **经典 TBox 没有这一元**；它是"规则"从描述升级为可执行契约的落点 |

**这就是 AOS 与传统本体论的分水岭**：传统本体的公理说明"什么必须为真"，AOS 的 ActionType 进一步规定"什么变更被允许发生、由谁、在什么前置条件下"。没有 ActionType，规则只能用来校验；有了 ActionType，规则可以**门控状态变更**。

### 5.2 T02 四构造（描述"复杂系统如何组织"）

```
ContextType / AggregateType / Mapping / ProcessType
```

| 构造 | 解决的问题 | 对应模式 |
|---|---|---|
| ContextType | 语义边界与通用语言（同一个词在不同上下文含义不同） | P-3 Bounded Context、P-8 Identity Context |
| AggregateType | 一致性边界、求值预算、不变量归属 | P-2 Aggregate 一致性边界 |
| Mapping | 跨上下文语义投影，且必须声明语义损耗 | P-5 声明式 Mapping |
| ProcessType | 跨聚合编排与补偿，唯一合法的流程出口 | P-9 ProcessType 跨聚合流程 |

四元组回答"有什么"，四构造回答"怎么组织"。二者都写在 `spec/` 的 YAML 声明里，由注册管线统一装载。

## 6. 概念映射矩阵：通用概念 → AOS 条款 → 代码构件

这张表是本指南最重要的一张——后续所有章节都围绕它展开。

| 通用本体论 / 知识图谱概念 | AOS 对应条款与术语 | 项目中的实际构件 |
|---|---|---|
| 类 Class | T01 ObjectType | `spec/ontology/objects/Contract.object.yaml` |
| 数据属性 / 对象属性 | T01 Property | `Contract.object.yaml` 的 `properties`；决策相关性标注对应 INV-8 |
| 关系 Relation / `is-a` / `part-of` | T09 结构性链接（LinkType）；跨上下文 `same_as` | `spec/ontology/links/same_as.link.yaml`，注册期三项校验 |
| 公理 / 规则 Axiom | T10 不变量三元组（声明+违规语义+修复绑定）、KS-3 受限解释、KS-7 SC | `spec/invariants/NoOrphanContract.invariant.yaml`；`src/interpreter/` |
| 个体 Individual | 本体事件日志中的领域对象状态（由事件投影得到） | `src/kernel/store.py`（append-only 流）、`src/kernel/projection.py`（只读视图） |
| 三元组断言 (S,P,O) | 带版本与出处的**事件**（KS-1.2），非 RDF 三元组 | `Event`：`event_id/stream_id/expected_version/event_type/payload/transaction_time/action_id/principal` |
| 模式层 TBox | 九类声明（**含 ActionType / ProcessType / 治理面声明**） | `spec/` 目录；`src/kernel/registration.py` 五步装载 |
| 数据层 ABox | 本体事件日志 + 投影 | `src/kernel/store.py` + `src/kernel/projection.py` |
| 推理引擎 | 受限解释器（布尔档 R10 / 映射档 R11） | `src/interpreter/boolean_profile.py`、`mapping_profile.py`、`audit.py` |
| 规则变更治理 | GOV-3 提案通道、GOV-2 工件哈希、创世窗口 KS-8 | `aos spec version`、`tools/hash_spec.py`、`src/kernel/genesis.py` |
| （无对应） | **会话事件流**（Agent 看到/想了什么，非本体状态） | `src/kernel/session.py`，物理独立存储 |
| （无对应） | **ActionType / 能力清单** | `spec/ontology/actions/*.yaml`、`config/capabilities.yaml` |

最后两行是 AOS 独有的：经典本体论没有"观测层与权威层分离"的要求，也没有"能力清单作为启动前置"的机制。

## 7. 三条不可混淆的边界

### 7.1 本体 ≠ 知识图谱（在本项目中）

AOS 用 TBox/ABox 做**教学类比**，但实现形态完全不同：

- 事实不是 RDF 三元组，而是**不可变事件流**；
- 查询不靠 SPARQL，而靠**可重建的只读投影**；
- 状态改变只有一条路：经 Action 评估后追加事件（AX-1 / INV-1）。

若带着"给我一个图数据库 + 三元组查询"的预期来用 AosKeel，会落空。

### 7.2 "显式规则"≠"写在文档里"

AOS 的规则必须**机器可执行**：声明式子语言编译成 Check AST，条件表达式编译成 `BooleanFunctionRef` 并在运行时由受限解释器求值（KS-7.1）。写在 Word / Markdown 里的业务规则，在 AOS 里不算规则。

### 7.3 "治理"不是附录，是内核前置

能力清单不完备 → 不发布能力清单 → **内核不启动**（VER-27 前置）；规范工件哈希漂移 → 拒绝并指向 GOV-3 版本通道。治理在这里是启动条件，不是事后审计。

---

## 8. 小结与下一站

- **本体 = 显式、形式化的概念/关系/属性/规则**；TBox 是蓝图，ABox 是按蓝图填充的事实。
- **AOS = 描述性本体 + ActionType + 治理**：四元组让本体能门控变更，四构造让它可以组织复杂系统。
- 三条独有的设计：**结构性链接零语义**、**会话流与权威流物理分离**、**能力清单作为启动前置**。
